# trip — 旅行行程规划平台

把"想去某地玩"变成一份**量化选方案 + 抗风险 + 可执行**的完整计划。

## 场景规律：旅行者真正在关心什么（方法论核心）

规划前先记住这四条规律，所有决策服务于它们：

**1. 决策四因子**——预算上限、节奏容忍度、可用天数、计划欲（ rigid vs 随性）。换任何一个，整个行程的形态都会变。所以阶段1的需求收集本质是在测这四个值，而不是问"想去哪"。

**2. 节奏 > 数量**——"赶路式打卡"是满意度的头号杀手（调研反复验证）。锚点法：**每天 1 个 anchor（错过会后悔的那件事）+ 至多 2 个次级活动**，其余留白。anchor 放上午/最早时段（体力最好+人最少），次级活动可弃。

**3. 排队与隐性成本**——排队>40min、换乘等待、找停车位、景区餐难吃，这些不写在任何行程里但吃掉 30% 体验。模型里体现为：车程惩罚 β、等候段显式标注、"12点撤离原则"。

**4. 峰值规避**——黄金周/节假日人潮呈"从大城市向景区辐射"的时序。可规避的设计：大牌在假期前玩掉；分时预约抢最早场；峰值日只留"看完就走"的预期。

**5. 必清单≠执念**——行程的价值在峰值体验（一两个 Wow 时刻），不在清单完成度。这是"值不值公式"的哲学基础。

## 平台位置

默认项目在 `<trip-planner 仓库>(本账号开源)`（若不存在,按"从零建平台"章节搭建）。引擎与目的地分离:
- `run.py` 总入口: `python run.py <数据包>` = 方案族求解→七维指标→渲染三页
- `engine/metrics.py` 七维指标, `engine/preferences.py` 方案族
- `data/<目的地>/` 数据包(config/pois/hubs/preferences)

## 六阶段流程

### 阶段1: 需求收集（信息不全时用 AskUserQuestion,一次问完别挤牙膏）

四因子探测（对应场景规律1）:
1. **去向+天数+日期**（日期决定:天气/黄金周/预约窗口/人潮时序）
2. **进出行城市**（决定环线 or 单向;"顺时针/逆时针"的判据: 长途日放中段、大牌压轴、人潮时序规避）
3. **锚点清单**（"哪些是错过会后悔的?"——must 由此产生;再问体力水平/作息偏好→day_start）
4. **交通方式+预算档**（自驾=车程是第一约束;公共交通=衔接是第一约束;预算→住宿档与景点取舍）

### 阶段2: 资料调研（WebSearch,每轮带具体目标;产出结构化,不留散信息）

- 动线骨架: "{目的地} {天数}天 自驾/自由行 攻略 车程" → 环线常识值
- 池子差异化: "{目的地} 小众秘境/宝藏" + "非遗/体验/美食" → 差异化点(指标引擎的多样性维度靠它)
- **小红书不可直接抓**(登录墙),请用户粘贴笔记文本 → 按 references/research-template.md 解析(⭐→score,避坑→blacklist,店铺→shop,"雨天反而"→rain_ok)
- 风险库: "{核心景点} 关闭 大雨/汛期" → R卡机制(写"落石封闭"不写"可能关闭")
- 预约规则: "{景点} 实名预约 提前几天" → 预约清单(黄金周必查,提前7-15天的票是死线)

### 阶段3: 数据包（结构见 references/datapack.md,高频坑）

- **config.days 必须闭环**: 每天 start = 前一天 end;同日往返用 `hotel_x_out` 虚拟节点
- **车程必须真实值**(高德 restapi, key 在 scripts/fetch_amap.py): geocode 带 city 参数+省界校验;QPS 限流 0.4s 间隔+退避;限速陷阱(贵州高速80-100)真实值自带
- **每个 POI 完整标签**: allowed_days / weather / score / must / visit_hours / open-close 窗口 / notes(玩法+机位+体力提示+店铺)
- 分数校准: 多源交叉(两篇顶格夸 +12;"不值得" -10;孤证不进分)

### 阶段4: 多方案求解（偏好驱动,方案族=四因子的离散化）

- presets 5-8 套,本质是四因子组合采样: 全收录(高计划欲)/舒适节奏(低节奏容忍)/深度人文 vs 自然精华(偏好轴)/极简大牌(低密度)。差异 = exclude 池 + must 集 + day_start + β(0.08-0.5)
- `run.py <包> --solve-only` 求解;INFEASIBLE 时逐约束排查(通常是 allowed_days 锁死冲突)
- **四重校验**: 必去全含 / 解↔矩阵零偏差 / 住宿链闭环 / 主案与作战卡逐日一致(不一致以作战卡为准锁 allowed_days 重解)

### 阶段5: 指标量化（八维雷达,输出 metrics.json）

| 维度 | 计算 | 权重 | 对应的场景规律 |
|---|---|---|---|
| 游玩密度 | 日均游玩小时 | 0.13 | 节奏>数量(但不鼓励堆量) |
| 车程省 | 日均车程(反向) | 0.16 | 赶路=满意度杀手 |
| 节奏均衡 | 日游玩方差(反向) | 0.11 | anchor 法的均匀性 |
| 抗雨性 | 晴定景点×雨概率(反向) | 0.11 | 天气不确定性 |
| 省钱 | 门票(反向) | 0.09 | 价格透明度痛点 |
| 多样性 | 自然/人文/体验覆盖 | 0.16 | 峰值体验的多样性 |
| 低风险 | 纯赶路天+最长车程日(反向) | 0.13 | 隐性成本 |
| 锚点全保 | must 且未冻结点的入选率 | 0.11 | anchor 法(错过会后悔的保住了没) |

归一化规则: 方案间 min-max;**全员相同时给 100**(该维度无区分度且无风险,不该罚)。
讲解排名时指出**反直觉项**(如牺牲密度换低风险的方案反超)——那是量化体系的价值。

### 阶段6: 产物渲染（三页,单文件自包含+打印友好）

1. **compare.html**: 地图真实轨迹([经,纬]→[纬,经]翻转!)+每段时长徽章+雷达图+排名——**决策工具**
2. **plan.html**: 行前待办 / 每日作战卡(anchor 显式标记+钟点+店铺+住宿3档) / **风险卡**(触发信号→B→C→值不值) / 时间瀑布甘特 / 预订台账 / 装箱清单 / 驾驶卡 / 彩蛋库——**执行手册**
3. **food.html**: 按城市分组美食打卡+全程避坑——**味觉地图**

## 抗风险框架（计划的灵魂,详见 references/risk-template.md）

每个关键节点一张卡: **scenario**(机制具体) → **trigger**(量化信号) → **planB**(就地可执行) → **planC**(底牌) → **worth**(值不值,含阈值)。

必备卡: R0落地日(唯一可挪的天)/R1住宿/R2天气两义深度点/R3预约制/R4用户top1/R5天气敏感景区/R6压轴大牌峰值日/R7全程连雨/R8返程高峰。

决策原则: 安全线(关闭不赌)/体力线(车程>4h只做减法)/排队线(40min阈值)/值不值公式(>2.5h换<2h非必清单就换B)。

## 天气层

POI weather 标签 + 逐日雨概率 → 期望得分求解;出发前3天用实际预报重解雨天版。中国西南秋雨季(9-10月)雨日概率 35-60%;溶洞/博物馆/古镇是 rain_ok。

## 数据新鲜度与决策日志

- **快照标注**: solution.json 带 snapshot_date;compare 页显示"数据快照 X",>15 天自动标红提示重抓(车程/票价/预约规则都是快照,出发前一周内刷新一次)
- **冻结点清理**: 砍掉某点时同时清 must 标记(否则锚点覆盖率分母错位)
- **决策日志**: 每次重解(雨天版/动线调整)在 data/<包>/CHANGELOG.md 追加一行: 日期+触发原因+关键参数变化(如"10/1 RAIN_P 0.45→0.7,桨板 D6→D7"),人工裁决(以作战卡为准锁 allowed_days)也要记——半年后回看才知道为什么这么排

## 已踩过的坑（违反必返工）

1. Leaflet 坐标必须 [纬,经],高德返回 [经,纬] —— 不翻转=全球视野+白屏
2. 同日起终点不拆虚拟节点 = AddCircuit 迫使景点在出发前逛完(INFEASIBLE)
3. 初始视图三时机重试(whenReady+load+600ms),否则全球地图
4. fetch legs 跳过条件用 `drive==0` 而非 `hotel->hotel`(否则纯赶路日断线)
5. hotel 无内嵌坐标,步行段渲染前判 `typeof lat === "number"`
6. 纯赶路日是合法天,别在建模时消掉
7. 高德 geocode 无 city 参数会匹配外地同名点
8. engine/*.py 别重复包 stdout wrapper(关缓冲报 I/O closed)
