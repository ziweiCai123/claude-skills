# 提取规则

## 什么算"学到"一项技术

- 用户**实际用了**或**深入讨论**了它（写代码、调试、问原理）→ 算，confidence 高。
- 只在对话里**顺带提到**（"顺便用了下 X"）→ 可记但 confidence 低（0.2–0.4）。
- 完全没出现 → **绝不**记。禁止为凑数臆造。

## confidence 打分

- **0.7–1.0**：动手操作过 / 深入讨论过原理 / 解决了相关问题
- **0.4–0.6**：有一定讨论但没深入
- **0.1–0.3**：仅一闪而过地提到

## 踩坑（最重要，宁可多记）

任何下列情况都算踩坑，记下【问题 + 根因 + 是否解决】：

- 报错 / 异常 / traceback
- 卡住、反复尝试、走错方向后纠正
- 误解了某个概念后被澄清

"是否解决"看会话末是否找到答案。**未解决也记**（标记 ❌），它同样是学习。
mistakes_resolved = 已解决的个数；mistakes_total = 含未解决的总数。

## 问题（questions 字段 = 数量）

挑**有代表性**的提问（理解概念、排查问题、怎么做 X），不要把每句话都算进来。一般 3–5 条。frontmatter 的 questions 字段填这个数量。

## 概念（写进"今天学到了什么"）

理解了的**抽象概念**（区别于具体工具名），如"声明式渲染""镜像分层""事件循环"。

## summary

一句**人话**，说清今天到底学了什么。不要套话（"今天收获很多"✗）。

## struggle_level

- **low**：顺利，没怎么卡
- **medium**：有几次卡顿或报错
- **high**：大量调试、反复试错

## 领域 / 主题识别（决定用横切还是主题分区）

- 判断今天内容是否跨**多个不相关领域**：技术栈 / 学科差异大才算（计算机 vs 生物医学、前端 vs 运维、算法 vs 工程）。
- 跨领域 → daily note 用**主题分区形态**（note-template 形态 B），frontmatter `domains` 列各领域。
- **同领域的不同技术不要硬分**（Docker + git 都属后端/运维，别拆）——过度切分反而碎。
- 主题名简短通用：计算机 / 生物医学 / 前端 / 后端 / 运维 / 算法 / 数据。用规范名保证跨天聚合一致。
- `domains` 与 `technologies` 的区别：domains 是**大领域**（2-5 个宽类），technologies 是**具体技术**（Docker / git / PCR）。

## 双链与技术名（Obsidian 协作）

- daily note 里的技术名用 Obsidian 双链包裹：`[[Docker]]`——同名技术在 Obsidian 里聚合到同一页、形成知识图谱。
- 技术名用通用规范写法（Docker 而非 docker / DOCKER），保证跨天链接到同一页、便于去重统计。
- 「🔗 与过去的连接」里引用历史笔记和其中技术都用双链：`进阶自 [[2026-06-30]] 的 [[Docker]]`。
- **日报/周报（reports/）绝不使用双链**——它们要 copy 进钉钉/飞书/邮件，`[[Docker]]` 字面量会污染文本；reports 保持纯文本。

## 红线

- 只从本次会话**真实内容**提取，禁止补全 / 臆造。
- 拿不准的就不记，别猜。
